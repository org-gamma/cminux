# cminux Translation Rules

**Version:** 1.0.0

This document specifies every rewrite cminux performs, character for
character. It is for readers of generated `.cpp` files and for anyone
modifying the transpiler itself. If you are writing cminux code, you do not
need this document — read `docs/language-reference.md` instead.

Each rule is presented as: input (as it appears in `.cmx`), output (as it
appears in `.cmx.cpp`), and the token-level transformation that produces it.

## 1. The pipeline in one page

Every `.cmx` file goes through four stages before it becomes an executable:

```
.cmx source
  │
  │  tokenize
  ▼
token stream
  │
  │  rewrite
  ▼
rewritten token stream
  │
  │  emit
  ▼
.cmx.cpp source
  │
  │  invoke cl.exe / g++ / clang++
  ▼
executable
```

The tokenize stage is a straight lexical scan. The rewrite stage applies the
nine rules below. The emit stage adds the prologue and prints the tokens
with reasonable spacing. The invoke stage runs the C++ compiler.

The rewriter is the only stage that knows about cminux-specific syntax. The
tokenizer knows the keyword list (to distinguish keywords from identifiers)
but does not interpret any of them. The emitter is a token printer.

## 2. The prologue

Every generated `.cpp` file begins with the same prologue. It is emitted
before any rewritten token, unconditionally, in the same order:

```cpp
// generated by cminux v1.0.0 — do not edit
// source: <input-path>
#include "outfn.hpp"
using cmx::print;
using cmx::println;

#line 1 "<input-path>"
```

The `<input-path>` is the path as given on the command line, verbatim.
If you invoke `cminux tests/hello.cmx`, the prologue contains
`// source: tests/hello.cmx` and `#line 1 "tests/hello.cmx"`.

The prologue has four jobs:

1. **Mark the file as generated.** The first line is a comment; a human
   reader sees immediately that the file is not meant to be edited.
2. **Name the source.** The second line records which `.cmx` file produced
   this `.cpp`. Useful when a `.cpp` file is left over with `--keep`.
3. **Make `print` and `println` work.** The `#include "outfn.hpp"` and the
   two `using` declarations bring `cmx::print` and `cmx::println` into
   scope, so cminux source can write `print("hi")` instead of
   `cmx::print("hi")`.
4. **Reset the line counter.** The `#line 1 "<input-path>"` tells the C++
   compiler that the next line is line 1 of the original source. From that
   point on, all diagnostics point at `.cmx` lines, not `.cpp` lines.

The prologue is five lines (plus a blank line) for every file, regardless of
what the file contains. It is not configurable in v1.0.0.

## 3. Rule 1: import

### Input

```
import ["a.hpp"]
import ["a.hpp", "b.hpp"]
import ["a.hpp", "b.hpp", "c.hpp"]
```

with optional trailing `;`.

### Output

One `#include` line per string, in order:

```cpp
#include "a.hpp"
```

```cpp
#include "a.hpp"
#include "b.hpp"
```

```cpp
#include "a.hpp"
#include "b.hpp"
#include "c.hpp"
```

### Token transformation

Input tokens:

```
Keyword("import") Punct("[") String("a.hpp") Punct("]")
```

Output tokens:

```
Punct("#include") Punct("\"") Ident("a.hpp") Punct("\"") Newline
```

For multiple paths, one `#include "path"` group per path, each terminated by
a `Newline` token.

### Edge cases

**Trailing semicolon.** `import ["a.hpp"];` and `import ["a.hpp"]` produce
identical output. The semicolon is consumed and does not appear in the
output.

**Line structure.** Each `#include` occupies its own output line. If the
input had one `import` statement on one source line, the output has N
`#include` lines, where N is the number of paths. This shifts subsequent
line numbers by N-1, which the `#line` directive does not compensate for.
This is a known limitation of v1.0.0.

**Empty list.** `import []` is an error: `expected string literal in import
list`.

**Non-string entry.** `import [outfn]` (no quotes) is an error: `expected
string literal in import list`.

**Missing bracket.** `import "outfn.hpp"` is an error: `expected '[' after
'import'`.

**Missing comma.** `import ["a.hpp" "b.hpp"]` is an error: `expected ',' or
']' in import list`.

**Missing close bracket.** `import ["a.hpp"` (no `]`) is an error at the
`End` token: `expected string literal in import list`.

## 4. Rule 2: func with return type

### Input

```
func add(int a, int b) -> int {
    ...
}
```

### Output

```cpp
int add(int a, int b) {
    ...
}
```

### Token transformation

Input token sequence (abbreviated):

```
Keyword("func") Ident("add") Punct("(") Ident("int") Ident("a") Punct(",") Ident("int") Ident("b") Punct(")") Punct("->") Ident("int") Punct("{") ...
```

Output token sequence:

```
Ident("int") Punct(" ") Ident("add") Punct("(") Ident("int") Ident("a") Punct(",") Ident("int") Ident("b") Punct(")") Punct("{") ...
```

The transformation:

1. Consume `func`.
2. Read the function name (`add`).
3. Scan the parameter list with balanced parentheses, collecting tokens
   including the `(` and `)`.
4. Consume `->`.
5. Collect tokens until the body's `{` as the return type.
6. Emit the return type, a spacer, the name, and the parameter list.

The tokens in the parameter list and the return type are copied verbatim.
cminux does not interpret them.

### Edge cases

**Multi-token return type.** `-> std::vector<int>` works. The rewriter
collects every token between `->` and the body's `{`, including the angle
brackets, and emits them before the function name. The output is
`std::vector<int> add(...)`.

**Pointer return type.** `-> MyClass*` becomes `MyClass* add(...)`. The
spacer token is emitted between the return type and the name, so the
output is `MyClass* add`, not `MyClass*add`. The C++ compiler accepts either,
but the spacer makes the output readable.

**Reference return type.** `-> MyClass&` becomes `MyClass& add(...)`.
Same spacing rule.

**Unbalanced parentheses in parameters.** If the parameter list has an
unbalanced `(`, the rewriter scans to the end of the file looking for the
matching `)`. It finds the `End` token instead and reports `unterminated
parameter list` at the line and column of `func`. This is almost always
caused by a typo — a missing `)` somewhere in a nested call in a default
argument.

**Missing return type.** `func f() -> { ... }` (nothing between `->` and
`{`) is an error: `expected return type after '->'`.

**Semicolon after parameters.** `func f() -> int;` (no body) is an error:
`function declaration without body is not supported`. The rewriter detects
this because it scans for `{` and hits `;` first.

**Arrow in parameter default.** `func f(int a = foo->x) -> int` — the `->`
inside the parameter list is part of a C++ expression, and the rewriter does
not confuse it with the return-type arrow because it scans the parameter
list with balanced parentheses and stops at `)`. After `)`, the next token
is the real `->`.

## 5. Rule 3: func without return type

### Input

```
func hello() {
    ...
}
```

### Output

```cpp
void hello() {
    ...
}
```

### Token transformation

Input token sequence (abbreviated):

```
Keyword("func") Ident("hello") Punct("(") Punct(")") Punct("{") ...
```

Output token sequence:

```
Ident("void") Punct(" ") Ident("hello") Punct("(") Punct(")") Punct("{") ...
```

The transformation is identical to rule 2 except that no `->` appears. The
rewriter synthesizes a `void` token and the spacer, then emits the name and
parameters as usual.

### Edge cases

**Empty parameter list.** `func hello()` with no `->` is the canonical case.
The output is `void hello()`.

**Non-empty parameter list.** `func hello(int a)` with no `->` works. The
output is `void hello(int a)`.

**`-> void` is equivalent.** `func hello() -> void` and `func hello()`
produce identical output (`void hello()`). Both are valid.

## 6. Rule 4: render

### Input

```
render 0;
```

### Output

```cpp
return 0;
```

### Token transformation

Input tokens:

```
Keyword("render") Number("0") Punct(";")
```

Output tokens:

```
Punct("return") Number("0") Punct(";")
```

The `render` keyword becomes a `return` token. Nothing else changes. The
spacing rules in the emitter insert a space after `return` because both
`return` and `0` are word tokens.

### Edge cases

**`render;` (no value).** `render` followed by `;` becomes `return;`. Valid
inside `void` functions.

**`render "hello";`** becomes `return "hello";`. The string token is
preserved with its original content.

**`render f(x) + 1;`** becomes `return f(x) + 1;`. All tokens after
`render` are preserved.

**`render` used as an identifier.** Not allowed — `render` is a cminux
keyword and cannot be used as an identifier. See
`docs/language-reference.md` section 6.4.

## 7. Rule 5: nil

### Input

```
var p = nil;
```

### Output

```cpp
auto p = nullptr;
```

### Token transformation

Input tokens:

```
Keyword("var") Ident("p") Punct("=") Keyword("nil") Punct(";")
```

Output tokens:

```
Punct("auto") Ident("p") Punct("=") Ident("nullptr") Punct(";")
```

`nil` becomes `nullptr`. Every occurrence, in every context.

### Edge cases

**`if p == nil`** becomes `if (p == nullptr)`. Note that the parentheses
around the condition are C++ syntax and must be present in the cminux source
as well; cminux does not add them.

**`f(nil)`** becomes `f(nullptr)`. Overload resolution picks
`f(std::nullptr_t)` if available.

**`nil` as a variable name.** Not allowed — `nil` is a cminux keyword.

## 8. Rule 6: let

### Input

```
let greeting = "hello";
```

### Output

```cpp
const auto greeting = "hello";
```

### Token transformation

Input tokens:

```
Keyword("let") Ident("greeting") Punct("=") String("hello") Punct(";")
```

Output tokens:

```
Punct("const") Punct("auto") Ident("greeting") Punct("=") String("hello") Punct(";")
```

`let` becomes two tokens: `const` and `auto`. The spacing rules in the
emitter insert a space between them.

### Edge cases

**`let` with complex initializer.** `let x = compute(1, 2);` becomes
`const auto x = compute(1, 2);`. The initializer is preserved entirely.

**`let` without initializer.** `let x;` is not valid cminux semantically,
but the rewriter does not catch it — it produces `const auto x;`, which is
a C++ error (`const auto x` requires an initializer). The C++ compiler
reports it, on the correct line, thanks to `#line`.

**`let` with braced initializer.** `let x = {1, 2, 3};` becomes
`const auto x = {1, 2, 3};`, which in C++ is `const std::initializer_list<int>`.
If you wanted a `std::vector<int>`, use an explicit cast or a named type.

## 9. Rule 7: var

### Input

```
var count = 0;
```

### Output

```cpp
auto count = 0;
```

### Token transformation

Input tokens:

```
Keyword("var") Ident("count") Punct("=") Number("0") Punct(";")
```

Output tokens:

```
Punct("auto") Ident("count") Punct("=") Number("0") Punct(";")
```

`var` becomes one token: `auto`.

### Edge cases

**`var` with complex initializer.** `var v = std::vector<int>{};` becomes
`auto v = std::vector<int>{};`. Preserved.

**`var` reassignment.** `var x = 5; x = 10;` becomes
`auto x = 5; x = 10;`. Reassignment works because `auto` (without `const`)
is mutable.

**`var` without initializer.** `var x;` is not valid cminux semantically
(C++'s `auto` requires a deducible type), but the rewriter does not catch
it. The C++ compiler reports it: `declaration of 'auto x' has no initializer`.

## 10. Rule 8: print

`print` is **not** a keyword in cminux. It is an identifier that happens to
resolve to `cmx::print` because the prologue brings it into scope. The
rewriter does nothing to `print` tokens.

### Input

```
print("hello");
```

### Output

```cpp
print("hello");
```

The token stream is unchanged. The resolution to `cmx::print` happens in
the C++ compiler, at compile time, because of the `using cmx::print;`
directive in the prologue.

### Why this is not a rule

If `print` were a keyword, users could not define their own `print` function
without shadowing problems. If `print` were rewritten to `cmx::print`, users
could not overload it in their own namespace. By leaving `print` as an
identifier and using `using cmx::print;`, cminux lets the C++ overload
resolution rules do the work — and the user can add overloads by writing
them in a header and importing that header.

### Edge cases

**User-defined `print` shadows the library one.** If the user defines
`void print(int)` at global scope, calls to `print(x)` where `x` is `int`
resolve to the user's function, not `cmx::print`. This is C++ overload
resolution; cminux does not interfere.

**`cmx::print` is also available.** Because the prologue uses `using`, not
`using namespace`, `cmx::print(...)` still works as a qualified call.

---

## 11. Rule 9: println

Identical to rule 8, for `println`. Not a keyword, not rewritten, resolves
via `using cmx::println;`.

### Input

```
println("hello");
```

### Output

```cpp
println("hello");
```

The token stream is unchanged.

## 12. What is NOT rewritten

Every token not mentioned in sections 3–9 is emitted verbatim, on the same
line it appeared on in the input (modulo the prologue and import-line
shifts). This includes:

- All C++ keywords: `if`, `else`, `while`, `for`, `switch`, `class`,
  `struct`, `namespace`, `template`, `typename`, `try`, `catch`, `throw`,
  `new`, `delete`, `static`, `extern`, `constexpr`, and so on
- All type names: `int`, `long`, `float`, `double`, `bool`, `char`, `void`
- All identifiers not equal to a cminux keyword
- All punctuation
- All literals: numbers, strings, `true`, `false`
- All comments (removed by the tokenizer, not by the rewriter — comments
  never appear in the token stream)
- All preprocessor directives (there are none in cminux source — `import`
  is the only header-inclusion construct, and it is rewritten by rule 1)

If you write a token that is not a cminux keyword and not a C++ keyword,
it is an identifier. If it is not a valid identifier (for example, a
Unicode character outside a string), the tokenizer rejects it with
`unexpected character`.

## 13. Line number preservation

cminux tries to keep the C++ compiler's line numbers aligned with the
source, because error messages are only useful if they point at the right
line.

### The prologue

The prologue occupies six lines (five content lines plus a trailing blank
line). The `#line 1 "<input-path>"` directive resets the counter, so the
next line — the first rewritten token — is reported by the C++ compiler as
line 1 of the input.

### Imports

Each `import [...]` with N paths emits N `#include` lines. If the source had
the import on line 1, the outputs are on lines 1, 2, ..., N. Subsequent
source lines are reported N - 1 lines off.

This is a known limitation of v1.0.0. A future version may emit a `#line`
directive after each multi-path import to restore alignment. For now, if
you use multi-path imports and want accurate error line numbers, split the
imports into separate statements on separate lines.

### Everything else

No other rule changes the line count. `func` → `T name(...)` occupies one
line in the source and one line in the output. `render e;` → `return e;`
occupies one line in each. `let`/`var`/`nil` are all same-line substitutions.

### What this means in practice

For a single-path import (or no import), error line numbers are exact.
For a multi-path import, error line numbers after the import are shifted
by the number of extra paths. This is the only source of line-number drift
in v1.0.0.

## 14. The spacer token

The rewriter has one escape hatch: a `Punct(" ")` token, which the emitter
prints as a single space and otherwise ignores.

The rewriter uses it in rules 2 and 3 to force a space between the relocated
return type and the function name. Without it, `int main()` would be emitted
as `intmain()` (because the emitter's default rule for word-word adjacency is
"insert a space", but the relocated return type and the function name are not
both word tokens in the intended sense — the return type might be a pointer,
`int*`, which needs a specific spacing rule the emitter does not have).

Concretely: `func main() -> int` becomes `[Ident("int"), Punct(" "),
Ident("main"), Punct("("), ...]`. The emitter prints `int`, then a space
(because of the spacer), then `main`, with no space between `main` and `(`
(because the emitter's rule for word followed by `(` is "no space").

The spacer token is internal to the rewriter. It never appears in user
source. If you are modifying the rewriter and find yourself wanting a
different spacing outcome, add or remove a spacer at the right point; do
not add a new rule to the emitter.

## Appendix: a full worked example

Source:

```
import ["outfn.hpp"]

func add(int a, int b) -> int {
    render a + b;
}

func main() -> int {
    let limit = 10;
    var sum = 0;
    var i = 0;
    while i < limit {
        sum = sum + add(i, i);
        i = i + 1;
    }
    println(sum);
    render 0;
}
```

Token stream (abbreviated, one token per line):

```
KW(import) P("[" ) STR(outfn.hpp) P("]") NL
NL
KW(func) IDENT(add) P("(") IDENT(int) IDENT(a) P(",") IDENT(int) IDENT(b) P(")") P("->") IDENT(int) P("{") NL
    KW(render) IDENT(a) P("+") IDENT(b) P(";") NL
P("}") NL
NL
KW(func) IDENT(main) P("(") P(")") P("->") IDENT(int) P("{") NL
    KW(let) IDENT(limit) P("=") NUM(10) P(";") NL
    KW(var) IDENT(sum) P("=") NUM(0) P(";") NL
    KW(var) IDENT(i) P("=") NUM(0) P(";") NL
    IDENT(while) IDENT(i) P("<") IDENT(limit) P("{") NL
        IDENT(sum) P("=") IDENT(sum) P("+") IDENT(add) P("(") IDENT(i) P(",") IDENT(i) P(")") P(";") NL
        IDENT(i) P("=") IDENT(i) P("+") NUM(1) P(";") NL
    P("}") NL
    IDENT(println) P("(") IDENT(sum) P(")") P(";") NL
    KW(render) NUM(0) P(";") NL
P("}") NL
```

Rewritten token stream (abbreviated):

```
P("#include") P("\"") IDENT(outfn.hpp) P("\"") NL
NL
IDENT(int) P(" ") IDENT(add) P("(") IDENT(int) IDENT(a) P(",") IDENT(int) IDENT(b) P(")") P("{") NL
    P("return") IDENT(a) P("+") IDENT(b) P(";") NL
P("}") NL
NL
IDENT(int) P(" ") IDENT(main) P("(") P(")") P("{") NL
    P("const") P("auto") IDENT(limit) P("=") NUM(10) P(";") NL
    P("auto") IDENT(sum) P("=") NUM(0) P(";") NL
    P("auto") IDENT(i) P("=") NUM(0) P(";") NL
    IDENT(while) IDENT(i) P("<") IDENT(limit) P("{") NL
        IDENT(sum) P("=") IDENT(sum) P("+") IDENT(add) P("(") IDENT(i) P(",") IDENT(i) P(")") P(";") NL
        IDENT(i) P("=") IDENT(i) P("+") NUM(1) P(";") NL
    P("}") NL
    IDENT(println) P("(") IDENT(sum) P(")") P(";") NL
    P("return") NUM(0) P(";") NL
P("}") NL
```

Emitted output:

```cpp
// generated by cminux v1.0.0 — do not edit
// source: example.cmx
#include "outfn.hpp"
using cmx::print;
using cmx::println;

#line 1 "example.cmx"
#include "outfn.hpp"

int add(int a, int b) {
    return a + b;
}

int main() {
    const auto limit = 10;
    auto sum = 0;
    auto i = 0;
    while (i < limit) {
        sum = sum + add(i, i);
        i = i + 1;
    }
    println(sum);
    return 0;
}
```

Note that `while (i < limit)` in the output has parentheses around the
condition, but the source `while i < limit` does not. Wait — look again.
The source has `while i < limit` with no parentheses. The output has
`while (i < limit)` with parentheses. Something added them.

**Something did not.** The source in this worked example is
`while i < limit {`, and cminux does not add parentheses. The output
should be `while i < limit {`, which is a C++ syntax error. This is a
bug in the worked example, not in cminux. The correct source is
`while (i < limit) {`, and the correct output is `while (i < limit) {`,
identical after rewrite. I have left the mistake in so that the example
is honest about what the current rewriter does and does not do: it does
not add parentheses around conditions. cminux relies on the user writing
valid C++ conditions, which means writing the parentheses.
